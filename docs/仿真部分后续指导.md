  # quadruped_control 后续分阶段实施计划

  ## 总体目标

  在不破坏现有 core → motion → RobotIO → backend 依赖边界的前提下，分阶段完成：

  1. 稳定 black 的 MotionRuntime 和 MuJoCo 仿真基线；
  2. 按 rl_sar 逻辑实现多策略切换和策略过渡；
  3. 完善行为/action 请求体系；
  4. 建立三进程 ROS 2 顶层接入；
  5. 在引入 blackW 前，整理三进程运行入口、统一构建入口和测试目录；
  6. 完成 blackW 资料确认、MuJoCo 模型、轮足控制和策略接入；
  7. 为后续真实 RobotIO 和硬件安全链路留下稳定接口。

  每个阶段由一个 agent 独立执行。agent 不跨阶段修改未授权范围；每阶段必须完成自己的代码、测试、文档更新和验收记录后再进入下一阶段。

  ———

  ## 阶段执行规则

  每个阶段 agent 必须：

  - 先阅读当前仓库和本计划中对应阶段；
  - 不修改其他阶段的目标；
  - 保留工作区中用户已有的未提交修改；
  - 不复制 black 和 blackW 两套源码树；
  - 不把 ROS 2、Torch、MuJoCo 或 SDK 引入 core/；
  - 为新增的 C/C++、Python、Shell、CMake 文件添加规定格式的中文文件头；
  - 使用 C++17；
  - 优先扩展现有测试，不为每个小改动新建大量测试文件；
  - 阶段结束时运行该阶段要求的最小构建和测试；
  - 在阶段总结中明确：
      - 修改了哪些文件；
      - 实现了哪些行为；
      - 运行了哪些命令；
      - 测试结果；
      - 尚未解决的问题；
      - 是否满足本阶段验收条件。

  除非某阶段明确要求，不得运行全量 profile，不得引入新的通用框架。

  ———

  - 不实现 ROS 2；
  - 不实现 blackW；
  - 不重构 RlController；
  - 不引入新的策略管理框架。

  默认 core/config/motion 测试
  MuJoCo 构建和 MuJoCo 测试
  RL profile 构建和 RL 测试

  至少验证：

  reset 后关节回到 MJCF 零位
  Passive → GetUp → Stand 成功
  Stand → RL Running 成功
  Running → Passive 成功
  Stand → GetDown → Passive 成功
  reset 后旧 session 命令和请求不再生效
  MuJoCo fault 后不继续接受正常命令

  ## 推荐验证命令

  ./scripts/build.sh
  ./scripts/build.sh --mujoco
  ./scripts/build.sh --rl

  # 阶段 2：完善 MotionRuntime 请求语义和终态交付

  ## 目标

  在实现多策略之前，先把 ModeRequest / ModeResult / MotionStatus 的生命周期语义固定下来，避免 ROS Action 和 GUI 输入各自解释状态。

  ## 工作内容

  - 审查并统一所有 ModeRequestType 的行为：
      - EnterPassive
      - GetUp
      - Stand
      - StartBehavior
      - GetDown
      - SwitchPolicy
      - ResetFault

  - 固定请求状态：
      - Rejected
      - Accepted
      - Running
      - Completed
      - Failed

  - 固定 request_id 去重和重试语义：
      - 相同 request_id 不重复执行；
      - 活动请求重试返回当前状态；
      - 已终态请求重试返回历史终态；
      - 旧 request_id 不覆盖新请求；
      - session 变化后旧请求不能继续执行；

  - 固定动作打断规则：
      - EnterPassive 可打断所有主动动作；
      - GetUp/GetDown 的互相打断行为明确；
      - 运行错误时活动请求必须得到 Failed；
      - 失败后 MotionRuntime 进入安全 Passive；

  - 固定 MotionStatus 字段的含义：
      - 当前模式；
      - 当前行为；
      - 行为阶段；
      - 当前策略；
      - 最近错误；
      - policy_ready。

  ## 决策约束

  - 不为每个行为增加新的公共 MotionMode；
  - 行为内部步骤通过 behavior_name 和 behavior_phase 表示；
  - 不让 ROS 消息类型进入 core；
  - 不使用异常跨越控制周期边界。

  ## 验收条件

  新增或扩展测试覆盖：

  请求重复提交
  请求乱序
  请求被打断
  请求跨 session
  请求在无状态时提交
  RobotIO fault 期间提交请求
  活动请求终态事件交付
  终态查询和 result_event 结果一致

  阶段结束后，后续 agent 可以直接把 ModeResult 映射为 ROS Action feedback/result，而不再自行推断。

  ———

  # 阶段 3：策略目录、策略加载和 rl_sar 风格策略切换

  ## 目标

  实现 flat/obstacle 等多个策略的注册、选择和切换，并按照 rl_sar 的逻辑支持运行中策略切换。

  ## 参考行为

  rl_sar 的策略切换不是简单替换指针，而是：

  收到策略切换请求
    → 确认目标策略存在
    → 判断当前姿态是否接近目标策略默认姿态
    → 若接近：直接 reload 目标策略
    → 若不接近：进入目标策略默认姿态的平滑 transition
    → transition 完成后重新初始化目标策略
    → 清空旧策略输出队列/历史
    → 切换成功后恢复 RL locomotion

  本阶段按这一行为实现，但使用当前仓库的固定容量 C++ 接口，不复制旧 FSM。

  ## 工作内容

  - 增加最小策略目录或策略注册接口；
  - 支持同时注册多个已加载策略；
  - 保持 TorchPolicy 负责模型加载、预热和 forward；
  - 让 MotionRuntime 负责：
      - 查找目标策略；
      - 验证策略名称；
      - 启动策略切换；
      - 清空旧 RlController 历史；
      - 更新当前策略名称；
      - 生成切换请求结果；

  - 实现 SwitchPolicy；
  - 实现两种策略切换路径：
      1. 当前姿态接近目标默认姿态时直接 reload；
      2. 当前姿态不匹配时，使用固定周期位置阻抗过渡到目标默认姿态；

  - 切换期间暂停旧策略推理；
  - 切换完成后重新初始化观测历史和动作目标；
  - 切换失败时：
      - 不保留半切换状态；
      - 清空 RL 命令；
      - 进入安全 Passive 或明确的安全恢复状态；
      - 返回 Failed；

  - 保持 flat 和 obstacle 的现有配置和模型路径不变。

  ## 重要语义

  - SwitchPolicy 可以在 Running 状态接收；
  - Running 期间切换不是立即替换控制输出；
  - 策略切换阶段输出固定位置阻抗命令；
  - 切换完成后恢复原 rl_locomotion 行为；
  - 切换期间 BaseCommand 可以继续接收，但不得驱动旧策略；
  - 切换失败不能继续执行旧策略的旧动作；
  - EnterPassive 在切换期间仍然拥有最高打断优先级。

  ## 建议接口方向

  可以扩展当前 attach_policy()，增加最小的多策略注册能力，例如：

  register_policy(name, RlConfig, Policy&)
  select/switch policy by name

  不要引入动态插件加载、脚本化行为图或通用 FSM 框架。

  ## 验收条件

  至少验证：

  flat → obstacle 直接 reload
  obstacle → flat 直接 reload
  姿态不匹配时先 transition 再 reload
  未知策略被拒绝
  策略未加载被拒绝
  策略加载失败返回 Failed
  切换期间旧策略不推理
  切换完成后 RL 历史被清空
  切换后 BaseCommand 仍然有效
  切换期间 EnterPassive 可打断

  并在 MuJoCo 集成测试中完成：

  GetUp → Stand → flat RL
  Running → SwitchPolicy(obstacle)
  obstacle RL → SwitchPolicy(flat)

  # 阶段 4：扩展真实需要的 behavior/action

  ## 目标

  在策略切换稳定后，按实际需求增加行为，不提前建设通用行为插件系统。

  ## 第一批行为

  优先只支持：

  rl_locomotion

  如需求已经明确，再按以下顺序增加：

  fixed_pose
  bridge_drive
  down
  himloco

  ## 每个行为必须明确

  新增行为时，agent 必须同时定义：

  - 行为名称；
  - 允许进入的 MotionMode；
  - 是否需要 BaseCommand；
  - 输出控制模式；
  - 行为内部阶段；
  - 完成条件；
  - 超时条件；
  - 失败条件；
  - 是否允许 EnterPassive 打断；
  - 是否允许策略切换；

  ## 推荐规则

  ### rl_locomotion

  Stand → Running
  持续运行
  需要 BaseCommand
  推理失败 → Failed + Passive

  ### fixed_pose

  Stand → Running
  输出固定姿态阻抗命令

  EnterPassive 可打断

  ### bridge_drive

  Stand → Running
  使用指定桥接控制规则
  BaseCommand 驱动
  控制失败 → Passive

  正常进入测试

  EnterPassive 打断测试
  session reset 测试

  不允许通过新增 MotionMode 枚举来表示行为内部步骤。

  # 阶段 5：ROS 2 消息和顶层接口设计

  ## 目标

  定义 ROS 2 顶层接口，但暂时不把 ROS 2 接入控制循环。先完成消息、命名、QoS 和请求语义，避免接口边做边改。

  ## ROS 2 接口方案

  采用“标准消息 + 少量自定义消息”的方式。

  ### 连续速度命令

  使用：

  geometry_msgs/msg/Twist

  映射：

  linear.x  → BaseCommand.vx
  linear.y  → BaseCommand.vy
  angular.z → BaseCommand.wz

  Adapter 使用本机 monotonic clock 生成 core 时间戳，不使用 ROS wall time 作为 StateFrame 或 BaseCommand 的内部时间。

  ### 一次性请求

  使用自定义 action/service：

  GetUp.action
  GetDown.action
  StartBehavior.action
  SwitchPolicy.action
  EnterPassive.srv
  ResetFault.srv

  最小自定义内容应能表达：

  - request_id；
  - 行为名；
  - 策略名；
  - 当前状态；
  - Accepted/Running/Completed/Rejected/Failed；
  - 错误消息。

  ### 状态发布

  至少发布：

  MotionStatus
  RobotIOStatus
  StateFrame 的低频诊断子集
  ModeResult

  不把高频完整 StateFrame 直接设计成 ROS 高频控制消息。

  ## QoS 和数据语义

  - /cmd_vel：只保留最新值，允许旧消息丢弃；
  - Action/Service：可靠；
  - 状态：低频、最新值；
  - 诊断：允许丢帧；
  - ROS callback 不直接调用 MotionRuntime::update()；
  - ROS 接口不能绕过 RobotIO 提交命令。

  ## 验收条件

  完成：

  ROS 接口包可独立编译
  消息字段与 core 类型有明确一一对应关系
  request_id 和 ModeResult 语义明确
  cmd_vel 超时规则明确
  策略切换 feedback/result 语义明确
  不修改 core 的第三方依赖边界

  ———

  # 阶段 6：三进程 ROS 2 仿真运行架构

  ## 目标

  采用三进程分层结构，而不是把 ROS callback、MotionRuntime 和 MuJoCo 物理循环全部塞进一个程序。

  ## 目标进程

  ros2_gateway
      ↓
  motiond
      ↓
  mujoco_backendd

  ### ros2_gateway

  职责：

  - ROS 2 topic/action/service；
  - 接收 /cmd_vel；
  - 接收 GetUp/GetDown/StartBehavior/SwitchPolicy；
  - 发布状态和反馈；
  - 不直接依赖 MuJoCo；
  - 不直接生成 CommandFrame；
  - 不直接调用 RobotIO。

  ### motiond

  职责：

  - 创建和运行 MotionRuntime；
  - 接收 BaseCommand 和 ModeRequest；
  - 读取 StateFrame；
  - 生成 CommandFrame；
  - 发布 MotionStatus 和 ModeResult；
  - 不依赖 ROS 2；
  - 可以使用本机 IPC adapter；
  - 不直接解析 ROS 消息。

  ### mujoco_backendd

  职责：

  - 创建 MujocoRobotIO；
  - 加载场景和 RobotModel；
  - reset/session；
  - 接收 CommandFrame；
  - 调用 step()；
  - 发布 StateFrame；
  - 管理 MuJoCo GUI 或 headless 模式；
  - 不依赖 ROS 2。

  ## 进程间通道

  第一版只实现 Linux 本机通道，不立即设计 STM32 网线协议。

  推荐：

  StateFrame / CommandFrame：
      固定容量共享内存，最新值覆盖

  BaseCommand：
      最新值共享内存或本机最新值通道

  ModeRequest / ModeResult：
      Unix Domain Socket 或可靠固定容量请求通道

  启动、reset、控制权：
      Unix Domain Socket 请求—应答

  通道必须传递明确的序列、session、startup、timestamp 和 schema version，不能直接传 C++ 对象内存到未来跨进程/跨机器协议中。

  ## 控制周期

  推荐：

  mujoco_backendd：按 MuJoCo physics timestep
  motiond：按 ControllerConfig.control_period_ns
  ROS gateway：由 ROS executor 调度

  motiond 不等待 ROS；mujoco_backendd 不等待 ROS；ROS 断开后控制进程仍按安全策略运行。

  ## 进程故障规则

  - ros2_gateway 退出：
      - motiond 的 BaseCommand 超时；
      - 速度归零；
      - 不影响控制线程继续运行；

  - motiond 退出：
      - mujoco_backendd 命令过期；
      - 回到安全 Disabled/Damping；

  - mujoco_backendd 退出：
      - motiond 读不到状态；
      - 活动请求 Failed；
      - 不继续产生有效主动命令；

  - IPC session 改变：
      - 旧帧、旧命令、旧请求全部拒绝。

  ## 验收条件

  完成一个无 GUI headless 端到端测试：

  启动三个进程
  → 建立 session
  → GetUp
  → Stand
  → StartBehavior(rl_locomotion)
  → 发布 cmd_vel
  → EnterPassive
  → GetDown
  → reset

  同时验证：

  ROS gateway 停止后速度命令超时
  motiond 停止后 MuJoCo 不再执行旧命令
  backend 停止后 motiond 返回失败
  重复/乱序/跨 session 帧被拒绝

  ———

  # 阶段 8：运行入口、构建入口和测试目录模块化

  ## 目标

  在引入 blackW 之前，先整理 black 当前已经完成的三进程仿真链路、构建入口和测试入口。
  本阶段不改变 MotionRuntime、RobotIO 和现有 action/service 的执行语义，主要改变启动方式、
  脚本组织、构建选择和文档说明；同时补齐三进程链路缺失的本地键盘、ROS 2 手柄输入，
  并将它们转换为现有 BaseCommand、ModeRequest 和后端控制请求。除为输入所必需的最小
  网关/IPC 接线外，不新增通用运行时框架，不在本阶段引入 blackW。

  阶段结束后，人工调试应当可以像 `rl_sar` 和 `real_robot` 一样，在三个独立终端分别
  启动后端、运动推理和顶层指令：

  ```text
  backend.sh
      ↓ StateFrame / CommandFrame
  motion.sh
      ↓ BaseCommand / ModeRequest
  command.sh
  ```

  三个进程必须继续使用当前固定容量 IPC 和当前 session/startup/过期语义，不能因为拆分
  启动脚本而增加第二套控制路径。

  ## 当前实现和本阶段要解决的问题

  当前已经存在三个独立可执行程序：

  - `quadruped_mujoco_backendd`：MuJoCo 物理后端，可选 headless/GUI；
  - `quadruped_motiond`：MotionRuntime 和 Torch 策略推理；
  - `ros2_gateway`：ROS 2 topic/action/service 到本机 IPC 的转换。

  阶段 8 后人工启动改为三个独立终端，分别运行 backend、motion 和 command。这样便于
  分别观察日志、单独重启一个模块，并仿照实机运行方式调试；ROS 2 launch 只保留自动化用途。

  当前脚本还混合了不同责任：

  - `scripts/build.sh` 是面向用户的统一构建入口，负责 CMake 构建和 CTest；
    `scripts/build/ros2.sh` 是 ROS 2 构建实现；
  - `scripts/test/ros2_headless.sh` 和 `scripts/test/ros2_headless_test.py` 负责三进程 E2E；
  - `scripts/run/backend.sh` 是 MuJoCo backend 的 GUI/headless 入口；
  - `scripts/debug/mujoco_sim.sh` 是单进程交互调试入口；
  - `scripts/run/motion.sh` 和 `scripts/run/command.sh` 分别负责运动推理与 ROS 2 指令。

  公共构建入口。

  ### 8.1 `scripts/run/backend.sh`

  这是所有仿真后端的统一用户入口，脚本名称固定为 `backend.sh`，不能再为每一个后端
  增加 `run_mujoco_backend.sh`、`run_isaac_backend.sh` 之类的用户脚本。

  当前只实现 MuJoCo，默认后端也是 MuJoCo。脚本至少支持：

  ```bash
  ./scripts/run/backend.sh
  ./scripts/run/backend.sh black
  ./scripts/run/backend.sh black plain
  ./scripts/run/backend.sh black terrain
  ./scripts/run/backend.sh black plain --mode headless
  ```

  参数语义：

  - 第一个位置参数是机器人名称，默认 `black`；
  - 第二个位置参数是场景变体，默认 `plain`；
  - 当前后端类型默认 `mujoco`，也应允许通过显式选项指定；
  - `--mode gui|headless` 选择运行时显示模式，默认 `gui`；
  - `--shm` 覆盖默认共享内存名称，默认根据机器人生成，例如
    `/quadruped_control_black`；
  - `--real-time-factor`、`--visual-sync-hz`、`--vsync` 继续传给 MuJoCo 后端；
  - `--robot-config`、`--scene` 等显式路径参数可以覆盖由 robot/scene 推导的默认路径。

  推荐同时支持更清晰的长选项形式：

  ```bash
  ./scripts/run/backend.sh \
      --robot black \
      --backend mujoco \
      --scene terrain \
      --mode gui
  ```

  当前参数解析不得实现 blackW 的特殊逻辑。脚本只负责根据 robot 和 scene 选择配置和
  资源路径，并调用当前 `quadruped_mujoco_backendd`。未来新增 backend 时，通过
  `--backend <name>` 进入分支；当前对除 `mujoco` 外的名称应明确报错，不得静默回退到
  MuJoCo。

  backend 脚本必须：

  - 从任意当前工作目录定位仓库根目录；
  - 检查 MuJoCo 依赖和后端可执行文件；
  - 不自动构建；
  - 不依赖 ROS 2 环境；
  - 默认由 backend 创建共享内存；
  - 将 Ctrl-C 转换为后端进程的正常退出；
  - GUI/headless 使用同一个后端程序和同一套 RobotIO 语义。

  ### 8.2 `scripts/run/motion.sh`

  这是运动推理统一入口，脚本名称固定为 `motion.sh`。

  建议支持：

  ```bash
  ./scripts/run/motion.sh
  ./scripts/run/motion.sh black
  ./scripts/run/motion.sh black flat
  ./scripts/run/motion.sh black obstacle
  ```

  参数语义：

  - 第一个位置参数是机器人名称，默认 `black`；
  - 第二个位置参数是初始策略名称，默认 `flat`；
  - 当前允许 `flat|obstacle`；
  - `--shm` 必须与 backend 使用的共享内存名称一致；
  - `--robot-config`、`--controller-config`、`--flat-policy-config`、
    `--obstacle-policy-config` 可以覆盖默认配置；
  - 其余参数直接传给 `quadruped_motiond`。

  推荐长选项形式：

  ```bash
  ./scripts/run/motion.sh \
      --robot black \
      --policy flat \
      --shm /quadruped_control_black
  ```

  motion 脚本内部应将 robot 解析为：

  ```text
  configs/robots/<robot>.yaml
  configs/controllers/<robot>.yaml
  configs/policies/<robot>/flat.yaml
  configs/policies/<robot>/obstacle.yaml
  ```

  不得为 black 和 blackW 复制两份 motion 启动逻辑。机器人差异必须通过路径和配置选择，
  具体字段校验仍由现有配置加载器和 MotionRuntime 完成。

  motion 脚本不得启动 ROS 2，不得启动 MuJoCo GUI，也不得直接读取键盘或手柄。它只负责
  启动独立推理进程，并等待 backend 创建共享内存。

  ### 8.3 `scripts/run/command.sh`

  这是 ROS 2 顶层指令入口。用户侧不再使用 ROS 2 launch 作为三进程主入口，也不把
  `ros2_gateway` 这个内部技术名称暴露为主要运行脚本名称。

  推荐脚本名称为 `command.sh`，因为它承载 `/cmd_vel`、action、service 和状态发布；
  `control.sh` 容易与 MotionRuntime 混淆，`gateway.sh` 仍然偏底层实现名称。

  使用形式：

  ```bash
  ./scripts/run/command.sh
  ./scripts/run/command.sh black
  ./scripts/run/command.sh --robot black --shm /quadruped_control_black
  ```

  command 脚本必须：

  - 检查 ROS 2 setup 和独立 colcon install 环境；
  - 检查 `ros2_gateway` 已安装；
  - 使用 robot 推导默认共享内存名称；
  - 允许 `--shm`、`--cmd-vel-timeout-ns` 等参数覆盖；
  - 只启动 ROS 2 顶层节点，不启动 backend 和 motion；
  - 不通过 ROS launch 隐藏其他两个进程；
  - ROS callback 继续只写 IPC，不调用 MotionRuntime。

  内部可继续使用现有的 ROS 包名 `quadruped_gateway` 和可执行程序名 `ros2_gateway`。
  本阶段优先整理用户入口名称，不为了美观立即重命名 ROS 包、接口包或内部 C++ 可执行文件，
  以避免无意义的 ROS API 和构建文件迁移。

  ### 8.4 本地键盘、手柄和人工输入接入

  阶段 8 不仅整理脚本，还必须补齐当前三进程仿真链路没有接上的人工输入。这里的
  关键边界是：**人工输入属于 command 进程，不能塞进 backend 或 motion 进程**。

  当前仓库已有两类容易混淆的旧实现：

  - `apps/mujoco_sim/terminal_input.*`：单进程 `mujoco_sim` 的终端输入，能够直接调用
    同一进程内的 `SimController` 和 `MotionRuntime`，不能直接复制到三进程运行链路；
  - `apps/mujoco_sim/sim_window.*`：MuJoCo 官方窗口的暂停、Reset 和相机交互，属于后端
    显示界面，不是 ROS 2 顶层的机器人指令输入。

  三进程模式下，终端键盘应由 `command.sh` 前台启动的 ROS 2 gateway 读取，手柄则通过
  ROS 2 的 `sensor_msgs/msg/Joy` 接入 gateway。backend 只负责物理、GUI 和 RobotIO；
  motion 只负责状态读取、策略推理和关节命令；command 负责把键盘、手柄、`/cmd_vel`、
  action 和 service 统一写成现有 IPC 数据。这样既保持和 `real_robot` 的“顶层控制器拥有
  输入、底层执行器只执行命令”边界一致，也不会让仿真出现第二套绕过 MotionRuntime 的控制路径。

  #### 8.4.1 参考实现的事实和可复用部分

  `rl_sar` 是手柄和 RL 运行时按键语义的主要参考：

  - `rl_sar/src/rl_sar/library/core/rl_sdk/rl_sdk.cpp` 的 `KeyboardInterface()` 使用
    `termios`/非阻塞读取，不要求回车，周期性读取单键；
  - `rl_sar/src/rl_sar/src/rl_real_mujoco.cpp` 订阅 `/joy` 和 `/cmd_vel`，按 F710 风格
    解析按钮、组合键和摇杆轴；
  - `rl_sar` 的基本语义是 `0` 起立、`9` 趴下、`P` 被动、`W/S/A/D/Q/E` 调整速度、
    `Space` 清零速度、`R` reset、`Enter` 暂停/继续、`N` 切换导航模式；手柄对应
    `A/B/X/Y`、`RB_Y/RB_X`、`LY/LX/RX` 等组合。

  `real_robot` 中没有一套可以直接复制到本仓库的完整四足 `/joy` 网关。可借鉴的是：

  - `real_robot/blackW/src/mujoco_runner/mujoco_runner/controller_demo.py` 和终端控制脚本
    的 `termios`/`tty`/`select` 非阻塞或半阻塞读取；
  - 退出时恢复终端设置；
  - 输入线程只改变控制状态，由固定周期控制回调发布命令；
  - 进入被动、关闭和异常时先停止主动输出，再退出节点。

  不能直接复制 real_robot 的 ROS 消息、电机数组、硬件标定、机械臂控制或高频命令发布；
  本仓库必须继续经过 `BaseCommand`、`ModeRequest`、`RobotIO` 和共享内存边界。

  #### 8.4.2 键盘输入的归属和生命周期

  `command.sh` 启动 `ros2_gateway` 时，若标准输入是 TTY，则默认启用本地键盘；若是
  headless、CI、管道或重定向输入，则自动禁用键盘读取，不得阻塞 ROS 2 spin。建议支持：

  ```bash
  ./scripts/run/command.sh black
  ./scripts/run/command.sh black --keyboard off
  ./scripts/run/command.sh --robot black --keyboard on --shm /quadruped_control_black
  ```

  gateway 内部只需要一个轻量的键盘输入循环和一个共享的人工输入状态，不要新增通用
  “输入框架”。键盘线程负责：

  1. 把终端切换为不回显、不等待回车的 cbreak/raw 模式；
  2. 使用 `select`/`poll` 或等价的非阻塞读取，不能阻塞 ROS 2 回调线程；
  3. 将按键写入一次性事件和持续速度目标；
  4. 在析构、Ctrl-C、异常和非交互启动时恢复原始终端设置；
  5. 不直接操作 MuJoCo、MotionRuntime 或关节命令，只调用 gateway 已有的 IPC 提交函数。

  键盘语义建议固定为：

  ```text
  0          GetUp action
  1          StartBehavior(rl_locomotion)
  2          SwitchPolicy(flat)
  3          SwitchPolicy(obstacle)
  9          GetDown action
  P          EnterPassive service
  R          请求 MuJoCo 后端 reset，建立新 session
  W/S        vx 增加/减少一个步长
  A/D        vy 增加/减少一个步长
  Q/E        wz 增加/减少一个步长
  Space      清零 vx、vy、wz
  N          在手动输入和导航输入之间切换
  X/Esc      仅关闭当前 command 进程
  H          打印当前帮助
  ```

  速度目标必须沿用当前单进程输入的限制、增量和单位：`vx/vy` 为 m/s，`wz` 为 rad/s，
  默认每次增量为 0.1，并在配置限制内裁剪。非 Running 状态下按速度键不得生成主动运动；
  可以提示一次并保持零命令。所有连续命令都必须带有限有效期，由 gateway 周期性刷新；
  键盘线程退出、输入超时或 command 进程退出后，`BaseCommand` 必须按已有超时语义失效。

  #### 8.4.3 手柄输入和 `/joy` 接口

  手柄底层设备读取和机器人控制语义应当分层。`ros2_gateway` 只订阅标准 ROS 2
  `sensor_msgs/msg/Joy`，负责按钮语义、摇杆语义、输入仲裁和 IPC；不在 gateway 内部
  直接打开 `/dev/input/event*`、解析 Linux joystick API，也不链接 SDL、pygame 或某个
  品牌 SDK。这样可以让仿真、真实 RobotIO 和测试发布器共用同一套 command 语义。

  但是，标准 `joy_node` 发布的 `Joy` 消息本身通常只有轴数组和按钮数组，没有控制器
  品牌名称。若要求“自动识别品牌并使用对应映射”，仅在 gateway 中订阅一个原始 `/joy`
  话题是不够的：gateway 无法可靠知道 `axes[3]` 到底是右摇杆 X 还是其他物理轴。因此
  阶段 8 采用如下折中方案：

  ```text
  物理手柄
      ↓
  controller_input（独立 ROS 2 输入适配节点，可自动热插拔和按品牌映射）
      ↓ 规范化 sensor_msgs/msg/Joy
  /joy
      ↓
  ros2_gateway（动作语义、输入仲裁、BaseCommand/ModeRequest/IPC）
  ```

  `controller_input` 是 command 侧的辅助输入进程，不是新的机器人控制进程；它只负责
  设备读取、设备名称匹配、轴/按钮重排、方向修正、死区和规范化输出。`command.sh` 在
  默认 `--controller auto` 模式下负责启动并清理它；没有手柄时该节点可以保持运行但发布
  disconnected/零状态，不得阻塞键盘和 ROS 2 gateway。有已有 `joy_node` 或真实机器人
  手柄节点时，可以使用 `--controller external --joy-topic /joy`，此时 command 不重复
  启动适配节点。

  仍然允许直接使用标准 `joy_node`，但此时必须显式指定已经确定的 profile，例如
  `--controller external --controller-profile xbox`；因为原始 `Joy` 消息不携带品牌信息，
  不应在“自动品牌识别”模式下把未知原始数组静默当作 Xbox 映射。

  ROS 2 gateway 包需要增加 `sensor_msgs` 依赖。Joy 回调必须先检查 `buttons` 和
  `axes` 长度，不能直接下标访问；缺少轴或按钮时应忽略对应输入并记录一次低频警告，
  不能崩溃、越界或产生 NaN。

  推荐第一版使用以下语义：

  ```text
  A              GetUp action
  B              GetDown action
  X              切换手动/导航输入模式
  Y              在 flat 和 obstacle 之间切换策略
  LB + X         EnterPassive service
  RB + Y         请求后端 reset
  左摇杆 LY     vx，LX 为 vy
  右摇杆 RX     wz
  ```

  摇杆需要死区、限幅和轴方向验证。F710 等设备通常把 LY 向上编码为负值，不能未经
  验证直接假设正负方向；应在仿真中确认“摇杆向前”产生正的机体 `vx`，并在帮助信息中
  写清当前设备映射。D-pad 和其他组合键可以先只做诊断或策略选择，不应在本阶段为每个
  未使用按键增加新的 MotionMode。

  手柄按钮是边沿事件，不能在一个按钮持续按下时每个 ROS 回调周期重复提交 action；
  手柄轴是连续命令，应使用最近一次接收时间和有效期刷新。手柄断开、`/joy` 超时、节点
  退出时，必须发布一次零手动速度并让命令自然过期，不能保留最后一个非零速度。

  #### 8.4.4 `real_robot/black/src/joypad` 参考结论和统一配置

  已阅读以下参考实现：

  ```text
  /home/windnotebook/PROJECT/Dog/real_robot/black/src/joypad/joypad/config.py
  /home/windnotebook/PROJECT/Dog/real_robot/black/src/joypad/joypad/joypad.py
  ```

  该实现有几项值得保留的事实：

  - 使用 pygame 以约 100 Hz 轮询手柄，并发布 `sensor_msgs/msg/Joy`；
  - 输出固定为 8 个轴和 12 个按钮，便于下游控制代码使用统一下标；
  - 通过手柄名称选择映射，并处理连接、断开、重新连接和状态清零；
  - 支持轴死区，参考默认死区为 `0.08`；
  - `StandardXbox` 使用接近 F710/Xbox 的标准按钮布局，左右摇杆、扳机和 D-pad
    分别映射到统一轴槽位；
  - `GaiShiXiaoJi`、`BeiTongBtpKp20d` 和 `ShaMoHu` 使用不同的物理轴重排和方向缩放，
    说明不能把所有手柄都当成同一套数组；
  - 参考代码通过 `frame_id` 区分连接/断开状态，但没有把设备名称放进标准 `Joy` 消息。

  参考实现也有需要改进的地方：品牌映射写成 Python 类并散落在代码中；未知设备直接
  回退到某个默认映射；设备名匹配规则不可由用户修改；轴、按钮和语义动作之间的层次
  混在一起；下游无法知道当前规范化数据来自哪个 profile。阶段 8 不复制这些类，而是
  使用一个统一的配置文件保存所有手柄 profile。

  推荐配置文件位置：

  ```text
  configs/input/gamepads.yaml
  ```

  推荐配置结构如下，实际字段名称可以根据现有 YAML 加载习惯微调，但必须保持“一个文件、
  多个 profile、配置数据和控制语义分离”：

  ```yaml
  # 物理手柄到规范化 Joy 数组的映射；不在此文件定义 GetUp 等机器人动作。
  output:
    axis_count: 8
    button_count: 12
    default_deadband: 0.08

  profiles:
    xbox:
      match:
        - "xbox"
        - "xinput"
        - "f710"
      axes:
        lx: {index: 0, scale: 1.0}
        ly: {index: 1, scale: -1.0}
        lt: {index: 2, scale: 1.0}
        rx: {index: 3, scale: 1.0}
        ry: {index: 4, scale: -1.0}
        rt: {index: 5, scale: 1.0}
        dpad_x: {index: 6, scale: 1.0}
        dpad_y: {index: 7, scale: 1.0}
      buttons:
        a: 0
        b: 1
        x: 2
        y: 3
        lb: 4
        rb: 5
        back: 6
        start: 7
        guide: 8
        left_stick: 9
        right_stick: 10

    gaitian_xiaoji:
      match: ["盖世小鸡"]
      # physical_index -> normalized_index
      axis_index: {0: 0, 1: 1, 3: 4, 2: 3, 5: 2, 4: 5}
      axis_scale: {0: -1.0, 1: -1.0, 2: 1.0, 3: 1.0, 4: 1.0, 5: 1.0}
      button_index: {0: 0, 1: 1, 2: 2, 3: 2, 4: 3, 5: 5,
                     6: 4, 7: 5, 8: 8, 9: 9, 10: 6, 11: 7,
                     12: 8, 13: 9, 14: 10}
  ```

  配置设计必须明确以下规则：

  1. `profile` 只描述物理设备到规范化数组的转换，不描述动作、策略或 MotionMode；
  2. 规范化轴名称固定为 `lx/ly/lt/rx/ry/rt/dpad_x/dpad_y`，规范化按钮名称固定为
     `a/b/x/y/lb/rb/back/start/guide/left_stick/right_stick`，下游再转换为数组；
  3. `match` 支持大小写不敏感的名称片段或正则/通配规则，匹配顺序必须稳定；
  4. 每个 profile 可以独立设置轴索引、方向、死区、限幅和扳机范围；不能只支持一个全局
     `axis_scale`；
  5. 未知设备不得静默使用可能危险的默认映射。应发布 disconnected/unknown 状态，或
     要求用户通过 `--controller-profile` 显式选择 profile；
  6. D-pad 必须单独描述来源（hat 或 axis），避免把 hat 事件和普通轴轮询重复写入；
  7. 映射配置加载失败、重复目标索引、越界索引、非法 scale 或缺少必需动作槽位时，输入
     适配节点应启动失败并给出明确错误；
  8. 规范化输出应固定长度，并在断开、异常和退出时发布零轴/零按钮或明确的 disconnected
     状态；不能把上一次非零状态继续保留。

  建议将 profile 选择分成三种模式：

  ```text
  auto      由 controller_input 根据设备名称和 gamepads.yaml 自动选择；未知设备不接管
  explicit  由 --controller-profile <name> 明确选择，适合标准 joy_node 原始输出
  external  不启动 controller_input，只消费用户指定的 /joy 话题
  ```

  `controller_input` 内部可以继续借鉴 pygame 的连接事件和轮询方式，但 pygame/SDL 依赖
  必须停留在该独立适配节点，不能进入 `core/`、`motion/`、`backends/` 或
  `ros2_gateway` 的 IPC 语义实现。若系统已有成熟的 `joy_node`，优先复用它；只有在需要
  自动品牌映射、统一输出长度和设备热插拔时才启动本仓库的 `controller_input`。

  #### 8.4.5 自动检测、默认键盘和手柄接管

  用户执行：

  ```bash
  ./scripts/run/command.sh
  ```

  时，默认行为应为：

  1. command 在 TTY 中启用键盘；
  2. 以 `--controller auto` 启动或监督 `controller_input`；没有手柄时继续只使用键盘；
  3. 适配节点匹配到合法 profile，并连续发布若干帧有效规范化 `/joy` 后，gateway 将
     手柄标记为 online；
  4. 手柄 online 后，手柄成为手动速度和手柄动作的主要输入源；键盘仍保留退出、Passive、
     Reset 等安全按键；
  5. 手柄断开或 `/joy` 超时后，gateway 立即清零手柄速度，并退回键盘；不重启
     MotionRuntime，不重启 gateway，不让最后一个速度残留；
  6. 手柄重新连接时，先清空按钮边沿状态并等待有效帧，再允许动作事件，避免重连产生
     假的 GetUp、GetDown、Reset 或策略切换。

  推荐 `command.sh` 选项：

  ```bash
  ./scripts/run/command.sh --controller auto
  ./scripts/run/command.sh --controller off
  ./scripts/run/command.sh --controller external --joy-topic /joy
  ./scripts/run/command.sh --controller auto \
      --controller-config configs/input/gamepads.yaml
  ./scripts/run/command.sh --controller explicit --controller-profile xbox
  ```

  `command.sh` 可以管理 `ros2_gateway` 和 `controller_input` 两个 command 侧进程，但不得
  把它们误认为两个独立的机器人控制进程。`controller_input` 退出时必须由 gateway 的
  `/joy` 超时和 command 清理逻辑共同保证零速度；command 脚本不能靠反复重启 gateway
  来完成输入切换。

  #### 8.4.6 输入仲裁和现有 ROS 指令的兼容

  现有 gateway 已经把 `/cmd_vel` 转成 `CommandSource::Navigation` 的 `BaseCommand`，
  并把 action/service 转成 `ModeRequest`。接入键盘和手柄后不能让多个回调直接竞争写入
  共享内存最新值；应在 gateway 内保留各输入源的最近值，由一个低频命令提交点选择最终
  的 `BaseCommand`。

  推荐保留 `rl_sar` 的“手动/导航模式”概念，同时保持当前 `/cmd_vel` 的兼容性：

  - 默认仍接受 `/cmd_vel`，不改变已有 ROS 2 用户的启动行为；
  - `N` 或手柄 `X` 进入手动模式后，键盘/手柄成为速度命令来源；
  - 再次切回导航模式后，恢复最近的、尚未过期的 `/cmd_vel`；
  - 无论选择哪种来源，最终只发布一份经过时间戳、有效期、限幅和有限值校验的
    `BaseCommand`；
  - action/service 仍然只走现有 `ModeRequest` 请求队列，不由键盘线程直接改变 MotionMode；
  - 本地手动速度建议使用一个明确的人工输入来源；若不扩展 `CommandSource`，至少必须在
    文档中说明键盘和手柄共用现有 `Gamepad` 来源，不能用 `Navigation` 冒充。若实现需要
    更准确的状态显示，可以在本阶段追加一个 `Manual` 来源值，并同步更新 core 校验和 IPC
    枚举映射，但不得借此重做优先级框架。

  `R` 的后端 reset 应复用已经存在的 `WireControlType::Reset` 控制队列和 session 校验，
  不得通过 shell 启动 `ipc_control`，也不得在 command 进程直接调用 MuJoCo。`Enter` 暂停/继续
  暂不强行映射到 command 进程：当前暂停状态由 MuJoCo GUI 所有，IPC 只有 Reset 控制请求；
  如果阶段实施确实需要三终端键盘控制暂停，必须另行增加幂等的后端 `SetPaused` 控制协议、
  结果和测试，不能把“切换暂停”伪装成 MotionRuntime 请求或直接改共享内存字段。

  #### 8.4.7 与三进程脚本的关系

  三个正式脚本的输入责任必须写清：

  ```text
  backend.sh    物理、GUI、后端 reset；不读终端机器人指令
  motion.sh     状态、推理、动作输出；不读终端、不订阅 /joy
  command.sh    键盘、/joy、/cmd_vel、action/service 和状态接口
  ```

  command 终端是三进程中唯一默认占用键盘的终端。backend GUI 仍可使用 MuJoCo 官方界面
  自带的相机、暂停和 Reset 控件，但这些控件不应被描述成 command 侧的机器人键盘控制。
  `all.sh` 若存在，必须把 command 的标准输入交给 command 进程，不能让三个子进程同时
  抢占同一个 TTY。

  ### 8.6 根目录可见性和工作区整理

  当前根目录同时展示源码模块、运行资源、生成物、临时日志和开发工具目录。对于使用者，
  最重要的是先看到“如何启动、核心模块在哪里、配置和资源在哪里”，而不是 build cache、
  ROS 日志或编辑器生成文件。阶段 8 只做低风险整理，不把所有源码强行迁移到新的 `src/`
  层级，避免与运行脚本和构建系统重构混在一起。

  推荐稳定的根目录布局：

  ```text
  quadruped_control/
  ├── adapters/          IPC、ROS 2 和外部接口适配
  ├── apps/              可执行程序和运行 daemon
  ├── backends/          MuJoCo 等仿真/执行后端
  ├── core/              无外部框架依赖的公共核心

  ├── policy/            策略适配器
  ├── config_loader/     配置加载实现
  ├── configs/           机器人、控制器、策略、输入和场景配置
  ├── assets/            MuJoCo 模型、网格和 TorchScript 等资源
  ├── scripts/           构建、运行、测试和调试入口
  ├── tests/             单元、MuJoCo 和三进程测试
  ├── docs/              设计、接口和运行文档
  ├── CMakeLists.txt
  ├── README.md
  └── AGENTS.md
  ```

  `build/`、`log/` 和根目录 `compile_commands.json` 不属于用户主视图。推荐改为：

  ```text
  .build/default/
  .build/mujoco/
  .build/rl/
  .runtime/log/
  .runtime/ros2/
  ```

  或继续使用 `/tmp/quadruped_control_*` 保存 ROS 2 临时工作区和运行日志。具体选择必须
  统一写入脚本，不能一部分脚本使用 `build/`、另一部分脚本使用 `.build/`。构建脚本不再
  在根目录创建 `compile_commands.json` 符号链接；编辑器直接指向所选 profile 的编译数据库。
  `.build/`、`.runtime/`、`__pycache__/` 和其他生成物必须由 `.gitignore` 忽略。

  `scripts/` 内部保持责任分区：

  ```text
  scripts/
  ├── build.sh                    公共构建入口
  ├── build/
  │   └── ros2.sh                 ROS 2 colcon 构建实现
  ├── setup/

  │   ├── backend.sh

  │   ├── ros2_headless.sh
  │   └── ros2_headless_test.py
  └── debug/                      单进程或历史人工调试入口
      └── mujoco_sim.sh
  ```

  不建议当前阶段把 `adapters/`、`apps/`、`core/` 等源码整体迁移到 `src/`。现有目录名
  正好反映 `core → motion → backend` 和 `command/adapters` 的架构边界，直接可见反而有利

  ## 三进程人工启动验收

  正式人工启动顺序必须明确写入 README 和运行文档：

  ```bash
  # 终端 1：先启动后端，由它创建共享内存
  ./scripts/run/backend.sh black plain

  # 终端 2：启动运动推理，等待并连接共享内存
  ./scripts/run/motion.sh black flat

  # 终端 3：启动 ROS 顶层指令
  ./scripts/run/command.sh black
  ```

  terrain 和 obstacle 示例：

  ```bash
  ./scripts/run/backend.sh black terrain
  ./scripts/run/motion.sh black obstacle
  ./scripts/run/command.sh black
  ```

  无头模式示例：

  ```bash
  ./scripts/run/backend.sh black plain --mode headless
  ./scripts/run/motion.sh black flat
  ./scripts/run/command.sh black
  ```

  三个脚本必须使用同一个共享内存名称。backend 退出后，motion 应按现有 backend
  disconnected 语义停止生成有效主动命令；command 退出后，BaseCommand 应按现有超时
  语义失效；不允许脚本层通过 kill 其他进程来掩盖这些运行时安全行为。

  ## 构建入口模块化

  对用户只保留一个公共编译入口：

  ```bash
  ./scripts/build.sh
  ```

  默认目标为全量构建，包括：

  ```text
  core/config/motion 基础 C++ 模块
  MuJoCo backend 和 GUI/headless 运行程序
  Torch motion 推理程序
  ROS 2 interfaces 和 command 网关
  ```

  建议支持以下选择：

  ```bash
  ./scripts/build.sh --target all
  ./scripts/build.sh --target core
  ./scripts/build.sh --target backend --backend mujoco
  ./scripts/build.sh --target motion
  ./scripts/build.sh --target command
  ```

  其中 `all` 是默认目标。`--clean`、`--no-test` 或等价的新参数继续保留，但构建脚本
  不应自动执行三进程 ROS 2 E2E。单元测试和 E2E 测试放在测试入口中显式执行。

  CMake 和 colcon 仍是两个底层构建系统，不能为了脚本合并而强行把 ROS 2 包并入主 CMake。
  `build.sh` 可以在内部调用两种构建流程，但用户只需要记住一个公共入口。不同依赖组合
  的 CMake cache 继续分开保存，例如：

  ```text
  build/default
  build/mujoco
  build/rl
  /tmp/quadruped_control_ros2_ws_stage7/latest
  ```

  缺少 ROS 2、MuJoCo 或 LibTorch 时，目标脚本必须给出明确的依赖提示，不得静默跳过目标。
  `scripts/build/ros2.sh` 是 `scripts/build.sh --target command` 使用的内部构建实现，
  不作为 README 的主要命令。

  ## CMake 构建边界要求

  当前 `apps/CMakeLists.txt` 只在 `QUADRUPED_ENABLE_MUJOCO` 下添加整个
  `runtime_daemons`，导致 motiond 和 MuJoCo backend 的构建条件耦合。本阶段应整理为：

  ```cmake
  if(QUADRUPED_ENABLE_MUJOCO)
      add_subdirectory(mujoco_headless)
      add_subdirectory(mujoco_sim)
  endif()

  if(QUADRUPED_ENABLE_MUJOCO OR QUADRUPED_ENABLE_TORCH)
      add_subdirectory(runtime_daemons)
  endif()
  ```

  具体实现必须保持：

  - backend 目标依赖 MuJoCo；
  - motion 目标依赖 Torch、MotionRuntime 和 IPC；
  - command 目标依赖 ROS 2 和 IPC wire adapter；
  - core 不依赖 ROS 2、Torch、MuJoCo 或电机 SDK。

  当前 `quadruped_mujoco_backendd` 直接链接 `quadruped_mujoco_gui`，因此 headless 构建
  仍可能需要 GLFW/OpenGL/PNG。若本阶段需要进一步拆分，应优先把 MuJoCo 物理后端和 GUI
  adapter 的编译依赖分开；可以仍保留一个支持 `--mode gui|headless` 的运行程序，不要为了
  构建整理新增不必要的通信进程。

  后端构建接口应为未来多个 backend 留出清晰选择，但当前只实现并验证 `mujoco`。不得
  现在引入 Isaac、硬件或新的通用 backend 框架。

  运行脚本和测试脚本必须分开：

  - `test/ctest.sh`：执行指定 CMake profile 的单元/MuJoCo 测试；
  - `test/ros2_headless.sh`：检查构建产物并调用现有 ROS 2 headless E2E；
  - `test/ros2_headless_test.py`：保留实际三进程测试逻辑；

  ## 命名和兼容原则

  用户侧名称统一为：

  ```text
  backend
  motion
  command
  ```

  其中：

  - `backend` 表示物理/硬件执行后端；
  - `motion` 表示 MotionRuntime 和策略推理；
  - `command` 表示 ROS 2 顶层指令和状态接口。

  对外运行参数采用“机器人 + 变体”的一致形式：

  ```text
  backend.sh [robot] [scene]
  motion.sh  [robot] [policy]
  command.sh [robot]
  ```

  当前默认值：

  ```text
  robot  = black
  backend = mujoco
  scene  = plain
  policy = flat
  mode   = gui
  ```

  不把所有第二参数都命名为 `model`：backend 的第二参数是 MuJoCo scene，motion 的第二
  参数是 Torch policy。用户界面可以保持位置参数风格，脚本内部必须使用 `scene_name`、
  `policy_name` 等准确变量名。

  不要因为名称美观而立即重命名 ROS package、ROS interface、IPC wire 字段或 core 类型。
  这些名称属于接口稳定性范围；本阶段只整理脚本、构建目标显示名和文档。如果确实需要
  重命名内部可执行文件，必须提供兼容路径并单独记录迁移，不得与 blackW 一起混改。

  ## 不做的内容

  - 不实现 blackW；
  - 不实现第二套绕过 command gateway 的键盘/手柄控制链路；
  - 不在 `ros2_gateway` 内实现手柄底层驱动、evdev/SDL 设备抽象或品牌 SDK；如需自动
    品牌映射，只允许在 command 侧独立的 `controller_input` 适配节点中实现最小设备读取，
    不得把设备依赖带入 core、motion 或 backend；
  - 不把 Enter 暂停/继续伪装为 MotionRuntime action；若要实现三进程暂停控制，必须单独
    设计幂等的后端控制协议；
  - 不改变 ROS 2 topic/action/service 名称和字段；
  - 不改变 BaseCommand、ModeRequest、ModeResult 或 MotionStatus 语义；
  - 不改变 IPC wire schema、session 或 startup 校验；
  - 不新增通用运行时框架；
  - 不实现第二种 backend；
  - 不删除单进程调试能力，只调整其位置和名称；
  - 不把 ROS 2、Torch、MuJoCo 引入 core。

      profile 的轴和按钮可按 `configs/input/gamepads.yaml` 转换；缺少轴/按钮、未知设备、

  11. `command.sh` 默认启用键盘，并能自动启动或连接 controller_input；手柄上线后自动
      接管手动输入，断开后自动退回键盘；显式 `off/external/profile` 选项行为明确，不能
      重复启动两个手柄发布器。

  12. 手动/导航输入切换不会破坏已有 `/cmd_vel`、action、service 语义；所有人工输入
      最终仍经过同一份 BaseCommand 或 ModeRequest IPC。
