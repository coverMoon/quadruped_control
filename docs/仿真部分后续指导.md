  # quadruped_control 后续分阶段实施计划

  ## 总体目标

  在不破坏现有 core → motion → RobotIO → backend 依赖边界的前提下，分阶段完成：

  1. 稳定 black 的 MotionRuntime 和 MuJoCo 仿真基线；
  2. 按 rl_sar 逻辑实现多策略切换和策略过渡；
  3. 完善行为/action 请求体系；
  4. 建立三进程 ROS 2 顶层接入；
  5. 完成 blackW 资料确认、MuJoCo 模型、轮足控制和策略接入；
  6. 为后续真实 RobotIO 和硬件安全链路留下稳定接口。

  每个阶段由一个 agent 独立执行。agent 不跨阶段修改未授权范围；每阶段必须完成自己的代码、测试、文档更新和验收记录后再进入下一阶段。

  ———

  ## 阶段执行规则

  每个阶段 agent 必须：

  - 先阅读当前仓库和本计划中对应阶段；
  - 不修改其他阶段的目标；
  - 保留工作区中用户已有的未提交修改；
  - 不复制 black 和 blackW 两套源码树；
  - 不把 ROS 2、Torch、MuJoCo 或 SDK 引入 core/；
  - 为新增的 C/C++、Python、Shell、CMake 文件添加规定格式的中文文件头；
  - 使用 C++17；
  - 优先扩展现有测试，不为每个小改动新建大量测试文件；
  - 阶段结束时运行该阶段要求的最小构建和测试；
  - 在阶段总结中明确：
      - 修改了哪些文件；
      - 实现了哪些行为；
      - 运行了哪些命令；
      - 测试结果；
      - 尚未解决的问题；
      - 是否满足本阶段验收条件。

  除非某阶段明确要求，不得运行全量 profile，不得引入新的通用框架。

  ———

  # 阶段 2：完善 MotionRuntime 请求语义和终态交付

  ## 目标

  在实现多策略之前，先把 ModeRequest / ModeResult / MotionStatus 的生命周期语义固定下来，避免 ROS Action 和 GUI 输入各自解释状态。

  ## 工作内容

  - 审查并统一所有 ModeRequestType 的行为：
      - EnterPassive
      - GetUp
      - Stand
      - StartBehavior
      - GetDown
      - SwitchPolicy
      - ResetFault

  - 固定请求状态：
      - Rejected
      - Accepted
      - Running
      - Completed
      - Failed

  - 固定 request_id 去重和重试语义：
      - 相同 request_id 不重复执行；
      - 活动请求重试返回当前状态；
      - 已终态请求重试返回历史终态；
      - 旧 request_id 不覆盖新请求；
      - session 变化后旧请求不能继续执行；

  - 固定动作打断规则：
      - EnterPassive 可打断所有主动动作；
      - GetUp/GetDown 的互相打断行为明确；
      - 运行错误时活动请求必须得到 Failed；
      - 失败后 MotionRuntime 进入安全 Passive；

  - 固定 MotionStatus 字段的含义：
      - 当前模式；
      - 当前行为；
      - 行为阶段；
      - 当前策略；
      - 最近错误；
      - policy_ready。

  ## 决策约束

  - 不为每个行为增加新的公共 MotionMode；
  - 行为内部步骤通过 behavior_name 和 behavior_phase 表示；
  - 不让 ROS 消息类型进入 core；
  - 不使用异常跨越控制周期边界。

  ## 验收条件

  新增或扩展测试覆盖：

  请求重复提交
  请求乱序
  请求被打断
  请求跨 session
  请求在无状态时提交
  RobotIO fault 期间提交请求
  活动请求终态事件交付
  终态查询和 result_event 结果一致

  阶段结束后，后续 agent 可以直接把 ModeResult 映射为 ROS Action feedback/result，而不再自行推断。

  # 阶段 3：策略目录、策略加载和 rl_sar 风格策略切换

  ## 目标

  实现 flat/obstacle 等多个策略的注册、选择和切换，并按照 rl_sar 的逻辑支持运行中策略切换。

  ## 参考行为

  rl_sar 的策略切换不是简单替换指针，而是：

  收到策略切换请求
    → 确认目标策略存在
    → 判断当前姿态是否接近目标策略默认姿态
    → 若接近：直接 reload 目标策略
    → 若不接近：进入目标策略默认姿态的平滑 transition
    → transition 完成后重新初始化目标策略
    → 清空旧策略输出队列/历史
    → 切换成功后恢复 RL locomotion

  本阶段按这一行为实现，但使用当前仓库的固定容量 C++ 接口，不复制旧 FSM。

  ## 工作内容

  - 增加最小策略目录或策略注册接口；
  - 支持同时注册多个已加载策略；
  - 保持 TorchPolicy 负责模型加载、预热和 forward；
  - 让 MotionRuntime 负责：
      - 查找目标策略；
      - 验证策略名称；
      - 启动策略切换；
      - 清空旧 RlController 历史；
      - 更新当前策略名称；
      - 生成切换请求结果；

  - 实现 SwitchPolicy；
  - 实现两种策略切换路径：
      1. 当前姿态接近目标默认姿态时直接 reload；
      2. 当前姿态不匹配时，使用固定周期位置阻抗过渡到目标默认姿态；

  - 切换期间暂停旧策略推理；
  - 切换完成后重新初始化观测历史和动作目标；
  - 切换失败时：
      - 不保留半切换状态；
      - 清空 RL 命令；
      - 进入安全 Passive 或明确的安全恢复状态；
      - 返回 Failed；

  - 保持 flat 和 obstacle 的现有配置和模型路径不变。

  ## 重要语义

  - SwitchPolicy 可以在 Running 状态接收；
  - Running 期间切换不是立即替换控制输出；
  - 策略切换阶段输出固定位置阻抗命令；
  - 切换完成后恢复原 rl_locomotion 行为；
  - 切换期间 BaseCommand 可以继续接收，但不得驱动旧策略；
  - 切换失败不能继续执行旧策略的旧动作；
  - EnterPassive 在切换期间仍然拥有最高打断优先级。

  ## 建议接口方向

  可以扩展当前 attach_policy()，增加最小的多策略注册能力，例如：

  register_policy(name, RlConfig, Policy&)
  select/switch policy by name

  不要引入动态插件加载、脚本化行为图或通用 FSM 框架。

  ## 验收条件

  至少验证：

  flat → obstacle 直接 reload
  obstacle → flat 直接 reload
  姿态不匹配时先 transition 再 reload
  未知策略被拒绝
  策略未加载被拒绝
  策略加载失败返回 Failed
  切换期间旧策略不推理
  切换完成后 RL 历史被清空
  切换后 BaseCommand 仍然有效
  切换期间 EnterPassive 可打断

  并在 MuJoCo 集成测试中完成：

  GetUp → Stand → flat RL
  Running → SwitchPolicy(obstacle)
  obstacle RL → SwitchPolicy(flat)

  # 阶段 5：ROS 2 消息和顶层接口设计

  ## 目标

  定义 ROS 2 顶层接口，但暂时不把 ROS 2 接入控制循环。先完成消息、命名、QoS 和请求语义，避免接口边做边改。

  ## ROS 2 接口方案

  采用“标准消息 + 少量自定义消息”的方式。

  ### 连续速度命令

  使用：

  geometry_msgs/msg/Twist

  映射：

  linear.x  → BaseCommand.vx
  linear.y  → BaseCommand.vy
  angular.z → BaseCommand.wz

  Adapter 使用本机 monotonic clock 生成 core 时间戳，不使用 ROS wall time 作为 StateFrame 或 BaseCommand 的内部时间。

  ### 一次性请求

  使用自定义 action/service：

  GetUp.action
  GetDown.action
  StartBehavior.action
  SwitchPolicy.action
  EnterPassive.srv
  ResetFault.srv

  最小自定义内容应能表达：

  - request_id；
  - 行为名；
  - 策略名；
  - 当前状态；
  - Accepted/Running/Completed/Rejected/Failed；
  - 错误消息。

  ### 状态发布

  至少发布：

  MotionStatus
  RobotIOStatus
  StateFrame 的低频诊断子集
  ModeResult

  不把高频完整 StateFrame 直接设计成 ROS 高频控制消息。

  ## QoS 和数据语义

  - /cmd_vel：只保留最新值，允许旧消息丢弃；
  - Action/Service：可靠；
  - 状态：低频、最新值；
  - 诊断：允许丢帧；
  - ROS callback 不直接调用 MotionRuntime::update()；
  - ROS 接口不能绕过 RobotIO 提交命令。

  ## 验收条件

  完成：

  ROS 接口包可独立编译
  消息字段与 core 类型有明确一一对应关系
  request_id 和 ModeResult 语义明确
  cmd_vel 超时规则明确
  策略切换 feedback/result 语义明确
  不修改 core 的第三方依赖边界

  ———

  # 阶段 6：三进程 ROS 2 仿真运行架构

  ## 目标

  采用三进程分层结构，而不是把 ROS callback、MotionRuntime 和 MuJoCo 物理循环全部塞进一个程序。

  ## 目标进程

  ros2_gateway
      ↓
  motiond
      ↓
  mujoco_backendd

  ### ros2_gateway

  职责：

  - ROS 2 topic/action/service；
  - 接收 /cmd_vel；
  - 接收 GetUp/GetDown/StartBehavior/SwitchPolicy；
  - 发布状态和反馈；
  - 不直接依赖 MuJoCo；
  - 不直接生成 CommandFrame；
  - 不直接调用 RobotIO。

  ### motiond

  职责：

  - 创建和运行 MotionRuntime；
  - 接收 BaseCommand 和 ModeRequest；
  - 读取 StateFrame；
  - 生成 CommandFrame；
  - 发布 MotionStatus 和 ModeResult；
  - 不依赖 ROS 2；
  - 可以使用本机 IPC adapter；
  - 不直接解析 ROS 消息。

  ### mujoco_backendd

  职责：

  - 创建 MujocoRobotIO；
  - 加载场景和 RobotModel；
  - reset/session；
  - 接收 CommandFrame；
  - 调用 step()；
  - 发布 StateFrame；
  - 管理 MuJoCo GUI 或 headless 模式；
  - 不依赖 ROS 2。

  ## 进程间通道

  第一版只实现 Linux 本机通道，不立即设计 STM32 网线协议。

  推荐：

  StateFrame / CommandFrame：
      固定容量共享内存，最新值覆盖

  BaseCommand：
      最新值共享内存或本机最新值通道

  ModeRequest / ModeResult：
      Unix Domain Socket 或可靠固定容量请求通道

  启动、reset、控制权：
      Unix Domain Socket 请求—应答

  通道必须传递明确的序列、session、startup、timestamp 和 schema version，不能直接传 C++ 对象内存到未来跨进程/跨机器协议中。

  ## 控制周期

  推荐：

  mujoco_backendd：按 MuJoCo physics timestep
  motiond：按 ControllerConfig.control_period_ns
  ROS gateway：由 ROS executor 调度

  motiond 不等待 ROS；mujoco_backendd 不等待 ROS；ROS 断开后控制进程仍按安全策略运行。

  ## 进程故障规则

  - ros2_gateway 退出：
      - motiond 的 BaseCommand 超时；
      - 速度归零；
      - 不影响控制线程继续运行；

  - motiond 退出：
      - mujoco_backendd 命令过期；
      - 回到安全 Disabled/Damping；

  - mujoco_backendd 退出：
      - motiond 读不到状态；
      - 活动请求 Failed；
      - 不继续产生有效主动命令；

  - IPC session 改变：
      - 旧帧、旧命令、旧请求全部拒绝。

  ## 验收条件

  完成一个无 GUI headless 端到端测试：

  启动三个进程
  → 建立 session
  → GetUp
  → Stand
  → StartBehavior(rl_locomotion)
  → 发布 cmd_vel
  → EnterPassive
  → GetDown
  → reset

  同时验证：

  ROS gateway 停止后速度命令超时
  motiond 停止后 MuJoCo 不再执行旧命令
  backend 停止后 motiond 返回失败
  重复/乱序/跨 session 帧被拒绝

  # 阶段 11：仿真故障注入、日志和回放基线

  ## 目标

  # 阶段 12：真实 RobotIO 和实机接入准备

  ## 目标

  在仿真和 ROS 2 语义稳定后，才进入真实硬件边界。

  ## 工作内容

  - 实现目标 black 的硬件 RobotIO；
  - 保持 RobotIO 是 motion 唯一边界；
  - 增加最终执行侧：
      - 电机通信；
      - 方向；
      - 减速比；
      - 零点；
      - 扭矩换算；
      - 速度/力矩限幅；
      - watchdog；
      - 急停；
      - 故障锁存；

  - 确认硬件校准不进入 motion normalized joint 数据；
  - 复用 MuJoCo、Replay、Fake 的 RobotIO 测试；
  - 先做单电机、台架、吊架，再做整机；
  - 真实硬件不可被 ROS 工具直接绕过安全链路控制。

  ## 验收条件

  单电机方向和换算正确

  命令过期进入阻尼/失能
  急停后无法直接恢复主动控制

  black 仿真和实机共享 MotionRuntime 行为

  blackW 实机接入应在 black 实机链路稳定后另开阶段，不与 black 首次硬件接入混做。
