# M2 基础运动闭环开发方案

- 状态：已完成（代码复审通过；起立和趴下效果已由用户观察带界面仿真后确认）
- 第一款机器人：black，12 自由度
- 实现范围：配置加载、MotionRuntime、带界面的 MuJoCo 基础运动闭环

本文是 M2 的编码和验收依据。长期模块边界以
[`quadruped_control_architecture.md`](quadruped_control_architecture.md) 为准，参考项目的
用途和优先级见 [`README.md`](README.md)。

## 1. 目标
M2 完成后，应能在不启动 ROS 2 和不加载 RL 策略的条件下，通过带界面的 MuJoCo 程序完成：

```text
Passive → GetUp → Stand → GetDown → Passive
```

具体目标：

1. reset 后关节保持 `Disabled`，机器人从空中默认姿态自然落地；
2. 用户在界面中请求起立时，MotionRuntime 记录落地关节姿态并执行 black 两段式起立；
3. 起立完成后进入独立的 `Stand`，持续保持默认站姿；
4. 用户请求趴下时，从当前姿态插值回首次起立前记录的落地姿态；
5. 状态机、请求去重、插值、命令帧和错误路径可以脱离 MuJoCo 自动验证；
6. 最终起立和趴下是否成功，以用户观察带界面仿真后的明确确认为准。

## 2. 非目标
M2 不实现：

- RL 观测、历史观测、LibTorch 推理和策略切换；
- ROS 2 Topic、Service、Action 和手柄适配；
- blackW 和比赛专用 behavior；
- 实机电机、IMU、共享内存、`robotd` 和 STM32H7；
- 噪声、延迟、回差、复杂地形和影子仿真；
- 通用插件框架或没有当前调用方的 behavior 注册系统。

M1 的 `mujoco_headless` 和无界面自动测试继续保留，供开环回归和确定性检查使用；它们不作为
M2 起立、站立和趴下的最终验收入口。

## 3. 路线调整
第一阶段后续顺序确定为：

1. M2：基础运动闭环；
2. M3：RL 行走闭环，先证明不依赖 ROS 2；
3. M4：ROS 2 外围接入；
4. M5：blackW 基础适配。

RL 先于 ROS 2 接入，避免外围通信方式反向决定 MotionRuntime 的内部结构。

## 4. 模块和依赖
M2 建议增加：

```text
config/                              启动期 YAML 配置加载和一致性检查
motion/                              MotionRuntime 和基础运动状态机
apps/mujoco_sim/                     带界面的交互式 MuJoCo 程序
configs/controllers/black.yaml       black 基础运动控制参数
```

依赖方向：

```text
config             → core + yaml-cpp
motion             → core
apps/mujoco_sim    → config + motion + backends/mujoco + MuJoCo/GLFW
```

约束：

- `core/` 继续不依赖 YAML、ROS 2、Torch 和 MuJoCo；
- `motion/` 不依赖 YAML、ROS 2、Torch、MuJoCo 或硬件 SDK；
- YAML 只在启动期读取，高频控制路径不读文件；
- 渲染和 GLFW 只存在于 `apps/mujoco_sim/`，不能进入 MotionRuntime 或 MuJoCo RobotIO；
- 配置加载完成后，MotionRuntime 只接收已经校验的命名类型。

## 5. 配置

### 5.1 RobotModel
补全并加载 `configs/robots/black.yaml`，至少包含：

- `model_id`、`calibration_id`；
- 12 个关节的名称、顺序和角色；
- 位置限制标志以及 M2 使用的速度、力矩、KP 和 KD 上限。

配置加载后必须调用核心 `validate(RobotModel)`。应用、测试和 MuJoCo 后端不能再各自维护一份
相互独立的 black 关节顺序。

### 5.2 ControllerConfig
black 控制器配置至少包含：

- 控制周期 5 ms；
- CommandFrame 有效期，第一版为两个控制周期；
- 两段起立和趴下的周期数；
- 预起立姿态、默认站姿；
- 每个关节的固定 KP、KD；
- 必要的命令跳变和输出限制。

数组长度、有限值、周期数、关节限制和关节顺序在启动时检查。配置不合法时拒绝启动，不能在
运行中使用部分默认值继续主动控制。

## 6. MotionRuntime 接口边界
MotionRuntime 通过 `RobotIO` 读取最新 `StateFrame` 并提交 `CommandFrame`。它不创建线程，
不推进 MuJoCo，也不读取键盘。

一次更新的输入包括：

- 当前单调时间；
- 最新有效的 `BaseCommand`（M2 可为空）；
- 本周期待处理的一个 `ModeRequest`（可为空）。

一次更新的输出至少包括：

- RobotIO 操作结果；
- 当前 `MotionStatus`；
- 请求存在时对应的 `ModeResult`。

构造或创建 MotionRuntime 时先验证 RobotModel 和 ControllerConfig。周期更新不能抛出异常
穿过 RobotIO 或控制循环边界。

## 7. 模式行为

### 7.1 Passive
- MotionRuntime 初始模式固定为 `Passive`；
- 每个关节显式使用 `ControlMode::Disabled`；
- reset 后机器人在重力作用下自然落地；
- Passive 不主动保持 XML 中的默认关节姿态。

后续实机最终执行侧仍可按自己的安全状态把 Disabled 覆盖为经过验证的阻尼退路。

### 7.2 GetUp
只在当前状态和执行侧安全状态允许时接受请求。首次从 Passive 开始起立时，完整复制当前 12 个
关节位置，作为当前控制会话的 `rest_pose`。

black 使用两段线性插值：

```text
当前落地姿态 → 预起立姿态 → 默认站姿
```

预起立姿态，按统一 FL、FR、RL、RR 顺序：

```text
FL:  0.0,  1.4, -2.2
FR:  0.0, -1.4,  2.2
RL:  0.0,  1.4, -2.2
RR:  0.0, -1.4,  2.2
```

第一段和第二段各 100 个成功控制周期，在 5 ms 周期下各约 0.5 s。命令使用
`JointImpedance`、目标速度 0、前馈力矩 0，以及配置中的固定 KP/KD。

只有状态读取、命令生成和 `submit()` 均成功时才推进插值周期。GetDown 期间重新请求 GetUp
时，从当时姿态重新执行起立，但保留原 `rest_pose`。

### 7.3 Stand
起立完成后自动进入 Stand，并完成原 GetUp 请求。Stand 持续发送默认站姿的
`JointImpedance` 命令。

M2 不允许从 Passive 通过 `Stand` 请求跳过起立。已经处于 Stand 时重复请求不得重新执行动作。

默认站姿：

```text
FL:  0.0,  0.82, -1.5
FR:  0.0, -0.82,  1.5
RL:  0.0,  0.82, -1.5
RR:  0.0, -0.82,  1.5
```

### 7.4 GetDown
GetDown 从请求被接受时的当前关节姿态，线性插值到本会话首次 GetUp 记录的 `rest_pose`。
第一版使用 500 个成功控制周期，在 5 ms 周期下约 2.5 s。

完成后自动进入 Passive，并完成原 GetDown 请求。尚未记录 `rest_pose` 时拒绝 GetDown，不能
猜测一套通用趴姿。

### 7.5 EnterPassive 和未实现请求
`EnterPassive` 可从任意运动模式立即中止主动动作并进入 Passive。M2 对
`StartBehavior`、`SwitchPolicy` 和 `ResetFault` 返回明确拒绝结果，不创建占位实现。

## 8. 请求编号和结果

同一控制会话内的内部 `request_id` 必须严格递增：

- 大于最近请求编号：作为新请求处理；
- 等于活动请求编号：作为重试，返回该请求的实时结果；
- 已终结的请求：重试或旧编号查询返回保存的终态；
- 小于最近编号且无保存终态：作为旧请求拒绝。

ROS 2 适配器以后负责把 Action UUID 映射为递增的内部请求编号。MotionRuntime 不无界保存
全部历史请求。

耗时请求依次报告 Accepted、Running 和 Completed，开始执行后因状态或 RobotIO 故障终止则
报告 Failed。被 GetUp 中断的 GetDown、被 EnterPassive 中止的主动请求和会话变化时被清除的
活动请求同样转为 Failed 终态。Rejected 请求不改变当前运动阶段。

所有终态都必须在产生周期通过更新输出交付：`result` 是输入请求处理时刻的快照
（Accepted/Rejected，或重试时的实时状态）；请求处理之后产生的终态（动作完成、中断、
失败，包括与输入请求同一编号的情况）经固定容量的 `result_events` 数组交付，容量 2 覆盖
最坏情况（旧活动请求终止 + 新动作随后失败），不需要动态分配。会话切换周期不处理
输入请求（拒绝并要求在后续周期重新提交），只交付旧请求终态，避免旧请求被自动重启
到新会话。该周期的 `Rejected("session changed; resubmit request")` 不参与编号去重、
不保存为终态，是要求重新提交的临时结果；后续适配层不得把它映射为不可重试的终态。
MotionRuntime 内部另保存最近 8 条终态用于重试查询，容量满时按最旧优先淘汰；淘汰后的
编号查询返回 Rejected（unknown），但已交付的结果不受影响。调用方需要长期保留的结果
应以交付事件为准，不能依赖内部历史。

## 9. 帧、会话和错误处理

M2 不修改现有公共帧字段：

- CommandFrame 复制当前执行侧状态中的 startup、session、model 和 calibration 标识；
- MotionRuntime 在新会话中从命令序号 1 重新开始；
- StateFrame 会话变化时立即回到 Passive，清除未完成请求和 `rest_pose`；
- `startup_id` 的双端线协议语义留到共享内存或 H7 通信设计前处理。

主动模式至少要求：

- StateFrame 通过核心校验；
- 关节在线且有效；
- 执行侧处于 `ControlEnabled`；
- 当前状态与配置的模型、会话和关节数量一致。

主动动作中条件失效时，请求转为 Failed，MotionRuntime 回到 Passive。无法提交新的 Disabled
命令时依赖旧命令过期，由 RobotIO 执行侧进入自己的安全退路。

## 10. 带界面应用

`apps/mujoco_sim/` 是 M2 的人工验收入口。它使用 MuJoCo C++ API 和 GLFW，运行单线程统一
调度的物理、控制和渲染循环。

第一版交互：

| 按键 | 行为 |
|---|---|
| `0` | 请求 GetUp |
| `9` | 请求 GetDown |
| `P` | 请求 EnterPassive |
| `R` | reset，建立新会话 |
| `Space` | 暂停或继续仿真 |
| `Esc` | 退出 |

界面和终端低频显示当前 MotionMode、请求结果、仿真时间和错误。键盘回调只更新输入副本，不能
直接运行状态机或推进物理。

M2 的起立和趴下最终验收流程：

1. reset 后观察机器人在 Disabled 状态自然落地；
2. 用户按 `0`，观察两段起立和 Stand 保持；
3. 用户按 `9`，观察机器人回到记录的落地姿态并进入 Passive；
4. 必要时调整经确认的参数后重复；
5. 只有用户明确确认视觉和运动结果成功，M2 才能标记完成。

自动测试通过不能替代第 5 项人工确认。

## 11. 验证计划

自动验证至少覆盖：

- 配置缺字段、数组维度、关节顺序、非有限值和越界参数；
- Passive、GetUp、Stand、GetDown 的合法和非法转换；
- 两段起立与趴下插值的起点、中间值、终点和控制模式；
- GetDown 返回首次记录姿态，以及 GetDown 被 GetUp 中断；
- EnterPassive、重复请求、旧编号和未实现请求；
- 会话变化、无状态、失效关节、安全状态下降和 submit 失败；
- CommandFrame 的标识、序号、有效期、维度和输出限制；
- 固定输入和请求时序下的可重复性。

MuJoCo 自动集成测试可继续无界面运行，用于检查帧、命令和有限值；M2 功能验收必须运行带界面
应用并由用户确认。

## 12. 实施任务

### M2-1：配置加载

建立隔离的 YAML 配置模块，补全 black RobotModel 和 ControllerConfig，消除应用与测试中重复的
black 模型定义。

### M2-2：MotionRuntime 基础

完成接口、配置检查、会话处理、请求编号、ModeResult 和 Passive。

### M2-3：基础运动状态机

完成 GetUp、Stand、GetDown、EnterPassive、插值和主动状态失败路径。

### M2-4：自动验证

增加状态转换、插值、请求、帧和错误路径测试，不引入第三方测试框架。

### M2-5：带界面 MuJoCo 应用

实现 GLFW 渲染、键盘输入、统一调度和低频状态显示；保留现有 M1 headless 程序。

### M2-6：人工验收与收尾

运行带界面完整流程，记录用户结论；只有用户确认成功后更新 README 为 M2 已完成。

## 13. 必须暂停并询问的情况

遇到以下情况不能自行调整参数掩盖问题：

1. Disabled 落地后的姿态无法安全执行参考起立流程；
2. 需要修改固定 MuJoCo 模型的关节方向、零点、惯量、接触或执行器范围；
3. 参考姿态与 RobotModel 限制冲突；
4. 需要修改 StateFrame、CommandFrame 或 RobotIO 公共字段；
5. 起立或趴下自动测试通过，但界面表现明显不合理；
6. 为实现渲染必须改变 MuJoCo 后端的依赖边界；
7. 用户尚未确认起立和趴下效果，却准备把 M2 标记为完成。
