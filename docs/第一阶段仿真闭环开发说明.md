# 第一阶段仿真闭环开发说明

- 状态：Draft v0.1
- 日期：2026-08-14
- 第一款机器人：black，12 自由度
- 开发范围：ROS 2 外围接口、MotionRuntime、MuJoCo 仿真

本文只说明第一阶段怎样落地。系统的长期边界和实机方案以
[`quadruped_control_architecture.md`](quadruped_control_architecture.md) 为准。

## 1. 第一阶段的目标

先完成一条可以实际运行和测试的仿真闭环：

```text
手柄 / 导航
      │ ROS 2
      ▼
ROS 2 适配器
      │ BaseCommand / ModeRequest
      ▼
MotionRuntime
      │ CommandFrame
      ▼
MujocoRobotIO ──运行物理仿真──┐
      ▲                       │
      └────── StateFrame ─────┘
```

完成后应能通过手柄或导航命令，让 black 在 MuJoCo 中完成：

1. 阻尼；
2. 起立；
3. 站立；
4. RL 行走；
5. 趴下；
6. 输入超时后自动把速度命令归零。

MotionRuntime 的代码中不能出现 ROS 2 消息、MuJoCo 类型或实机电机协议。

## 2. 暂时不做什么

第一阶段不开发：

- 实机电机和 IMU；
- `robotd`、共享内存和控制权申请；
- STM32H7 和上下位机协议；
- Fast DDS 封装；
- 实机姿态镜像和影子仿真；
- 完整日志回放系统；
- blackW 的比赛专用状态和事件链。

这些功能不应阻碍接口设计，但暂时不为它们编写没有调用方的代码。

## 3. 开发方式

不要按照“先把 ROS 2 全部做完，再把 MotionRuntime 全部做完，最后开发 MuJoCo”的顺序进行。

三个模块应围绕一条最小闭环一起增长：

```text
公共接口
   ↓
MuJoCo 能接受一帧简单命令
   ↓
MotionRuntime 能产生阻尼和位置命令
   ↓
ROS 2 能发送一次模式请求
   ↓
逐步加入起立、RL 和调试信息
```

这样可以尽早发现关节顺序、时间、控制模式和命令超时等接口问题。

## 4. 建议的代码目录

建议新建独立工程，不直接在 `rl_sar` 和现有 `mujoco_runner` 中继续堆功能：

```text
quadruped_control/
├── core/                 公共数据结构、RobotModel、RobotIO
├── motion/               MotionRuntime、状态机、策略运行
├── backends/
│   └── mujoco/           MujocoRobotIO
├── adapters/
│   └── ros2/             ROS 2 输入、请求和状态输出
├── apps/
│   └── mujoco_sim/       组装并启动完整仿真
├── configs/
│   ├── robots/           关节名称、顺序和限制
│   ├── controllers/      周期、增益和限幅
│   └── policies/         策略模型及输入输出说明
└── tests/
```

第一版可以将三个模块组装在同一个进程中。模块独立不等于必须拆成多个进程。

依赖方向固定为：

```text
ROS2Adapter ─┐
MotionRuntime├──→ core
MujocoRobotIO┘

MotionRuntime → RobotIO
```

`core` 不能依赖 ROS 2、Torch、MuJoCo 和某个电机 SDK。

## 5. 公共接口先做到什么程度

### 5.1 数据结构

第一版定义：

- `StateFrame`：关节、IMU、帧序号和生成时间；
- `CommandFrame`：关节控制模式、目标值、帧序号和有效期；
- `BaseCommand`：`vx`、`vy`、`wz`、来源和有效期；
- `ModeRequest/ModeResult`：模式请求、请求编号和结果；
- `MotionStatus`：当前阶段、功能、策略、命令来源和错误；
- `RobotModel`：机器人名称、关节名称、顺序、功能角色和限制。

关节数据优先使用固定最大容量和有效关节数量，避免控制周期中反复分配内存。第一版最大容量可设为 16，以覆盖 black 和 blackW。

### 5.2 RobotIO

第一版 RobotIO 只需要：

```text
读取最新 StateFrame
提交最新 CommandFrame
读取连接和仿真状态
```

实机控制权、共享内存和下位机通信以后再扩展。接口中不能出现 MuJoCo 对象或 ROS 2 消息。

### 5.3 旧 ROS 消息

现有 `RobotCommand/RobotState` 缺少时间、序号、有效期和明确控制模式，不能直接作为新的内部接口。

如果旧工具仍需使用，可以在 ROS 2 适配器中提供临时兼容转换，但 MotionRuntime 和 MujocoRobotIO 不能依赖这些旧消息。

## 6. MotionRuntime 第一版

MotionRuntime 对外提供一次控制更新，而不是自己创建 ROS 线程：

```text
输入：最新 StateFrame、BaseCommand、待处理 ModeRequest、当前时间
输出：CommandFrame、ModeResult、MotionStatus
```

第一版包含：

- 命令来源选择和超时归零；
- `Passive/Damping`；
- `GetUp`；
- `Stand`；
- `Running`，第一个注册的功能为 `rl_locomotion`；
- `GetDown`；
- 策略观测构建和历史观测；
- TorchScript 推理；
- 输出缩放、限幅、跳变检查和 NaN/Inf 检查。

暂不移植策略热加载、比赛事件链以及 blackW 的过桥、钻杆等专用功能。
后续它们以新 behavior 的形式注册，不增加公共 MotionMode。功能内的姿态过渡和执行步骤
由各 behavior 自己管理。

### 6.1 从现有代码提取什么

可以参考或提取：

- black/blackW 的 YAML 参数；
- 状态进入、运行和退出时的运动行为；
- 起立和趴下插值；
- 观测顺序、缩放、裁剪和历史观测；
- TorchScript 模型加载和输出换算。

需要重新实现：

- 主循环和线程管理；
- ROS 2 回调；
- 键盘和手柄到状态机的直接判断；
- 状态、命令和策略输出的数据所有权；
- 配置路径和程序启动方式。

状态机只能读取 `BaseCommand/ModeRequest`，不能读取键盘编号、手柄按钮编号或 ROS 字符串。

## 7. MuJoCo 第一版

建议使用 MuJoCo C/C++ API，实现进程内的 `MujocoRobotIO`。现有 Python `mujoco_runner` 保留为行为参考和迁移前的对照程序。

第一版实现：

- 加载场景 XML；
- 根据关节名称建立映射；
- reset 到默认姿态；
- 接收 Disabled、Damping、JointImpedance、Velocity 和 Torque 命令；
- 计算 PD 加前馈力矩；
- 执行物理步进；
- 读取关节位置、速度、力矩和 IMU；
- 生成 StateFrame；
- 支持有界面、无界面、实时和不限速运行。

第一版不加入额外噪声、延迟、回差和 GapModel。基本闭环稳定后，再从现有 Python 程序逐项迁移，并为每项功能增加开关。

关节和执行器必须按名称匹配。发现缺失、重复、维度不一致时直接拒绝启动，不能退化为根据数组下标猜测。

## 8. 仿真控制时序

仿真由一个主循环统一推进，不使用三个互相独立的壁钟线程分别运行物理、控制和推理。

black 的第一版参考频率为：

| 内容 | 周期 |
|---|---:|
| MuJoCo 物理步进 | 由模型设置，例如 1～2 ms |
| MotionRuntime | 5 ms，200 Hz |
| RL 推理 | 每 4 个控制周期一次，50 Hz |
| ROS 2 状态显示 | 20～100 ms |
| MuJoCo 渲染 | 约 30～60 Hz |

主循环行为：

```text
处理最新的 ROS 2 输入
        ↓
到达控制时刻时，读取 StateFrame 并运行 MotionRuntime
        ↓
保持最新 CommandFrame，执行若干 MuJoCo 物理小步
        ↓
生成下一份 StateFrame
```

实时模式只限制运行速度，不改变控制结果。无界面不限速运行时，相同初始状态和输入应产生可重复的结果。

ROS 2 回调只更新输入副本，不能直接运行状态机、策略推理或 MuJoCo 步进。

## 9. ROS 2 外围第一版

第一版只接入已有系统真正需要的接口：

| ROS 2 接口 | 转换结果 |
|---|---|
| `/cmd_vel` | 导航来源的 BaseCommand |
| `/joy` | 手柄来源的 BaseCommand 和 ModeRequest |
| 模式 Action | 起立、趴下、阻尼、站立和切换策略 |
| MotionStatus Topic | 当前阶段、功能、策略、输入来源和错误 |
| `sensor_msgs/JointState` | 关节状态显示 |
| `sensor_msgs/Imu` | IMU 显示 |
| 仿真 Service | reset、pause 和单步 |

起立和趴下需要一段时间完成，优先使用 ROS 2 Action。适配器把 Action Goal UUID 转换为内部请求编号，并把执行进度和最终结果返回给调用方。

现有导航继续发布 `geometry_msgs/Twist`，第一阶段不重写导航程序。

MuJoCo 真值里程计和 GapModel 属于仿真传感器或感知测试数据，不放入 RobotIO，也不作为 MotionRuntime 的固定输入。需要时由独立 ROS 2 发布器读取 MuJoCo 的只读快照。

## 10. 配置拆分

第一阶段至少分成三类配置：

| 配置 | 第一版内容 |
|---|---|
| RobotModel | 机器人名称、关节名称、顺序、功能角色和限制 |
| ControllerConfig | 控制周期、起立参数、KP/KD 和命令限幅 |
| PolicyManifest | 模型文件、观测顺序、动作顺序、缩放、默认姿态和 decimation |

MuJoCo XML 中的关节和执行器名称必须与 RobotModel 对照检查。PolicyManifest 的关节顺序也必须显式核对，不能因为数组长度都是 12 就认为一致。
源 URDF/MJCF 可以因工具限制把轮子写成大转角范围的 `revolute`，但 RobotModel 仍要
明确记为轮子角色且不启用位置限制。轮子命令使用 `JointImpedance`，通常为
`KP=0 + 目标速度 + KD`，不为此另造一套命令结构。

black 跑通后，通过新增配置和模型支持 blackW，不复制 MotionRuntime 或 MujocoRobotIO 源码。

## 11. 开发里程碑

### M0：公共接口

- core 可以在不安装 ROS 2、Torch 和 MuJoCo 的条件下编译；
- StateFrame、CommandFrame、RobotModel 和 RobotIO 有基础测试；
- 错误的关节数量、名称、时间和控制模式会被拒绝。

### M1：MuJoCo 开环

- black 模型可以加载、reset 和无界面运行；
- Disabled、Damping 和 JointImpedance 行为正确；
- 关节名称和执行器映射经过检查；
- 固定输入可以重复得到相同结果。

### M2：基础运动闭环

- MotionRuntime 完成 `Passive → GetUp → Stand → GetDown → Passive`；
- 不依赖 ROS 2 即可通过测试程序驱动；
- 状态机切换、插值和输出限幅有自动测试。

### M3：ROS 2 接入

- 手柄和 `/cmd_vel` 能驱动仿真；
- BaseCommand 超时后速度自动归零；
- 模式 Action 能返回接受、执行中、完成或失败；
- RViz 或 PlotJuggler 能看到关节、IMU 和 MotionStatus。

### M4：RL 行走

- 固定 StateFrame 输入下，新旧程序的观测向量一致；
- 相同观测下，策略输出和关节目标一致或误差在确定范围内；
- black 可以在 MuJoCo 中稳定站立和行走；
- 推理超时或输出非法时进入阻尼或安全站立状态。

### M5：blackW

- 通过新 RobotModel、ControllerConfig 和 PolicyManifest 支持 16 自由度；
- black 和 blackW 共用 MotionRuntime 与 MujocoRobotIO；
- 轮关节和腿关节使用明确的功能角色和位置限制标志。

## 12. 第一阶段验收条件

满足以下条件后，才开始实机和 STM32H7 路线：

1. MotionRuntime 编译时不依赖 ROS 2 和 MuJoCo；
2. 不启动 ROS 2 时，测试程序仍能完整运行仿真闭环；
3. ROS 2 Adapter 退出或停止更新，不会阻塞控制循环；
4. `/cmd_vel` 和手柄命令超时后自动归零；
5. 模式请求不会因为重复发送而重复执行；
6. black 能完成阻尼、起立、站立、行走和趴下；
7. headless 模式支持自动测试和快于实时运行；
8. 关节名称、顺序或策略维度错误时拒绝启动；
9. 新旧策略的观测和输出已经通过固定样本对比；
10. 关键循环能记录周期、执行时间和超时次数。

## 13. 正式编码前先确定的事项

开始搭建代码时先完成下面三个小决定：

1. 确定第一版编译标准和依赖获取方式，建议 C++17、CMake、LibTorch、MuJoCo 和 GoogleTest；
2. 将 MuJoCo 作为明确的 CMake 依赖安装或配置，不能硬编码当前 Python 包目录；
3. 选定一份唯一的 black MuJoCo XML 和一份唯一的策略配置作为基准，其他重复目录只作为历史参考。

当前已固定使用 MuJoCo 3.9.0 Linux x86_64 官方发行包。发行包由
`scripts/setup_mujoco.sh` 下载和校验，安装在不提交的 `.deps/` 目录，不使用
Python 或 Conda 包中的动态库。

完成这三项后，从 M0 和 M1 开始建立工程，不先移植完整 RL 状态机。
